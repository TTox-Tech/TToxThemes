TToxThemes — PRD & Dev Plan
17 Nov 2026 · @TTox.Tech
1. Summary
TToxThemes is a modular glass desktop kit for Debian-family Linux (Kali first) on KDE Plasma and XFCE: three restrained palettes, a top pill bar, a side mini-dock, placeable desktop widgets, a live-metrics HUD and a devtools drawer, all generated from one palette file and switched with one command. The visual target is the approved interactive mock; the design values live in the Design Spec doc.
Goals
• G1. The desktop matches the approved mock: one-sheet glass windows with a light outline, terminal as the most transparent surface, pill bar, mini-dock, bare clock.
• G2. Wallpaper-led: the user's own illustration drives the tone; the kit picks the closest palette and nudges only the accent.
• G3. Widgets are placeable, resizable and saved per profile; adding a widget needs no change to the core.
• G4. Runs on any Debian-family distro; features degrade one tier at a time instead of failing the install.
• G5. Lite mode keeps the look and stays usable on a 2 GB VM without 3D acceleration.
• G6. Every change the installer makes is backed up and reversible with one command.
Non-goals for v1: light variants, GNOME, Hyprland/niri, Wayland-only features, per-workspace layouts, a GUI settings app, publishing to an apt repository.
What a 2-hour build can and cannot deliver. The code for every pack can be written, generated and statically checked in this session (Python runs, shell syntax, config parse, unit tests for the generator and the metrics daemon). It cannot be run on a real Plasma or XFCE session here: there is no display, compositor or Kali machine in the build environment. So v1 ships as "written and statically verified"; the first real install is on your machine, in the order given in section 10, and anything that fails there is a fix round, not a surprise. Parts most likely to need that round: Kvantum SVG recolour, Plasma panel scripting, Klassy/Panel Colorizer versions, eww window geometry.

4. Functional requirements A: look
Every requirement has an ID; section 10 tests against these IDs.
Palettes and tokens
ID
Requirement
FR-P1
Three palettes ship: Sterling (silver + steel blue), Vino (black + wine), Graphite (grey + copper), with the exact hex values in the Design Spec section 3.
FR-P2
A palette is 7 neutrals, 2 text tones, accent, accent2, accent_text, folder tint, and ok / warn / err. No generated file may contain a colour outside the active palette.
FR-P3
Accent appears only on: selection, focus ring, active tab underline, default button, prompt glyph, focused-app indicator, launcher glyph, toggles that are on.
FR-P4
Terminal 16-colour set stays on-palette: blue/magenta/cyan slots map to accent and palette greys.
FR-P5
All sizes, radii, opacities, fonts and durations come from one tokens file; no target hardcodes them.
FR-P6
Adding a palette is one dictionary entry plus a generator run; no other file changes.
FR-P7
The generator is deterministic: same inputs give byte-identical output.
Glass and performance modes
ID
Requirement
FR-G1
Opacity ladder per mode (full / balanced / lite): terminal 50 / 62 / 88 %, window body 62 / 72 / 92 %, bar and dock 70 / 76 / 92 %, popups 72 / 78 / 94 %.
FR-G2
Blur: 14 px + 5 % noise in full, 8 px + 3 % in balanced, off in lite. Terminal uses the strongest blur available.
FR-G3
Mode off disables compositing entirely; reachable by flag only.
FR-G4
Switching mode is live (no logout) and changes blur, opacity, shadows, animation set and metrics poll interval together.
FR-G5
Readability guard: when the wallpaper region behind a surface is bright, that surface's opacity is raised until text contrast is at least 4.5:1; the guard is computed once per wallpaper, not per frame.
FR-G6
Install picks the mode automatically: lite in a VM or without GL, balanced on integrated graphics with under 6 GB RAM, full otherwise; the user can override.
Windows
ID
Requirement
FR-W1
A window is one glass sheet: titlebar and body share colour and opacity, separated by a 1 px line at 30 %.
FR-W2
Active window: 2 px outline in fg at 60 %; inactive: 1 px line colour. Corner radius 12 px.
FR-W3
Titlebar 32 px, title left-aligned as ❯ name in mono; buttons right: maximise, close; close hover uses err. Minimise button configurable, off by default.
FR-W4

FR-W6
Terminal: 12 px padding, no menubar, no scrollbar, tab bar hidden under two tabs, block cursor, no blink, prompt ❯ in accent with path on the line above.
Wallpaper
ID
Requirement
FR-WP1
ttox-theme --wallpaper <file> sets the wallpaper, picks the closest palette by neutral temperature and luminance, and nudges accent by at most 12° hue and 10 % saturation toward the image's dominant mid-tone.
FR-WP2

FR-WP3

FR-WP4

Widgets
ID
Requirement
FR-WD1
A widget is a folder: widget.toml (id, title, sizes, providers needed, default position), a view file, optional script. Dropping a folder into the user widgets directory makes it available; no core file changes.
FR-WD2

FR-WD6

FR-WD8
Widgets read colours and sizes only from the generated tokens stylesheet; switching palette or mode restyles them without restart.
FR-WD9

If eww is unavailable, a conky fallback renders clock + sparklines + system summary at fixed positions and the installer says widgets run in fallback mode.
Metrics daemon (ttoxd)
ID
Requirement
FR-M1
One user-level daemon polls and writes a single JSON document; every consumer reads that file. Schema is versioned and documented.
FR-M2
Providers are plugins: system, network, sensors, battery, gpu, docker, k8s, git, ci, services, ports, vpn, media, updates, pomodoro, kali. A provider runs only while a visible widget or enabled bar module needs it.
FR-M3
Poll interval 1 s / 2 s / 5 s by mode; slow providers (public IP, CI, updates) have their own longer intervals and cache.
FR-M4
A provider that raises or times out is isolated: its section reports error with a message, others continue.
FR-M5
The daemon never runs as root. Privileged reads go through a small polkit helper with a fixed command list.
FR-M6
ttox-theme --metrics prints the current JSON; --metrics <provider> one section.
FR-M7
Runs as a systemd user service with restart on failure; ttox-theme --doctor reports its state.

Requirement

6. Functional requirements C: install, CLI, portability
Installer
ID
Requirement
FR-I1
install.sh runs interactively or fully by flags: --de kde|xfce|auto, --variant, --mode auto|full|balanced|lite, --packs core,kde,widgets,..., --with-boot, --offline, --dry-run, --yes.
FR-I2
Capability detection, never a distro-name check: package manager is apt; then DE and version, session type (X11 / Wayland), GL renderer, virtualisation, RAM, battery, available packages, presence of each optional tool.
FR-I3
Before changing anything, every file to be touched is copied to a timestamped backup directory and listed in a manifest.
FR-I4
Idempotent: running twice yields the same state and no duplicate config blocks.
FR-I5
--dry-run prints every package, file and setting that would change and exits without changes.
FR-I6
Each pack installs in its own step; a failed step is reported with the reason and the tier reached, and the rest continue. Exit code is non-zero only if core fails.
FR-I7
Missing packages are installed with apt after one confirmation listing them; nothing is installed from a third-party apt source. Components not in the distro's repositories (eww on some releases, Klassy, Panel Colorizer, picom animation fork, fonts, icons, cursor) are fetched from pinned upstream release URLs with SHA-256 verification, or skipped with a clear fallback.
FR-I8
Shell files are edited only inside a marked block (# >>> ttox >>> ... # <<< ttox <<<).
FR-I9
User-level by default: nothing under /etc or /usr changes unless --with-boot or the login-screen step is accepted.
FR-I10
uninstall.sh restores every backed-up file, removes what the kit added, and leaves installed apt packages alone unless --purge-packages is given.

8. Architecture
Four layers with one-way dependencies: tokens → generator targets → appliers → runtime (daemon + widgets). Nothing downstream is edited by hand; it is regenerated.
TToxThemes/
  palettes.py            # colours (the only file edited for colour)
  tokens.py              # ladder, radii, fonts, motion, sizes
  build/
    generate.py          # discovers build/targets/*.py, writes dist/
    lib.py               # colour maths, rgba/mix, contrast, file helpers
    wallpaper.py         # adapter + generated fallback + readability guard
    targets/             # one module per output family, each: render(ctx) -> {path: content}
      colors.py          # colors.scss/.css/.sh/.json consumed by everything at runtime
      kde_*.py  xfce_*.py  shell_*.py  term_*.py  apps_*.py  boot_*.py
  src/                   # static assets copied as-is (QML, SVG bases, templates)
  dist/                  # generated: dist/<pack>/<target>/ttox-<variant>[-<mode>]...
  scripts/
    lib.sh               # log, have, backup, state, confirm, marked-block edit
    detect.sh            # capability detection -> key=value
    apply_kde.sh  apply_xfce.sh  apply_shell.sh  apply_apps.sh  apply_boot.sh
  widgets/
    ttoxd/               # daemon: core loop + providers/*.py + schema
    eww/                 # eww.yuck, eww.scss, windows: bar-modules, desktop, hud, gallery, cheatsheet
    library/<id>/        # one folder per widget: widget.toml, view.yuck, script
    profiles/*.toml      # minimal, work, pentest, music
    conky/               # fallback
  bin/ttox-theme         # CLI
  install.sh  uninstall.sh  Makefile  debian/  tests/  vendor.lock  README.md  LICENSE

Data flow at runtime: providers → ttoxd → metrics.json → eww deflisten → bar modules, desktop widgets, HUD. Palette or mode switch: CLI → repoint current/ symlinks → run appliers → reload eww, rofi, notifications, compositor.
Why this shape: the target-module contract is what lets six people (or agents) build in parallel without touching each other's files, and it is the same seam a future palette, DE or app theme plugs into.
